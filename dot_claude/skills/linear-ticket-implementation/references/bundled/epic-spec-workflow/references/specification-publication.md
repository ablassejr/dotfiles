# Specification publication

Publish the approved behavior and its sources in the documentation home selected for the project. A repository revision, versioned shared document, wiki record, or shared artifact can carry the specification. Keep semantic records and the coherent design explanation in their owning sections or documents; do not create separate copies merely because several connectors are available.

Resolve the actual source revision, destination, existing record, audience, and authorization before writing. Prepare the complete content and media first. If the destination is missing, deliver the prepared draft and ask only when publication is a required next action. A request to draft does not require choosing a new documentation service.

Preserve stable semantic identities, source links, approval evidence, and supersession where the scope uses them. Bind review to exact content through an available revision or reconstructable snapshot and content hash. An editable page title is not sufficient identity. A local snapshot establishes prepared bytes; publication and team access need their own evidence.

Perform authorized writes with the provider's supported concurrency and retry controls. Afterward fetch the saved content, revision, associations, and media; compare them with the prepared result. Inspect rendering when a permitted viewer exists and disclose unavailable checks under `design-document`. Verify audience access as far as tools allow. Partial or mismatched writes remain incomplete; reconcile existing records before retrying rather than duplicating them.

Use the scope's established approval path. Approval covers the exact reviewed content and does not itself prove publication or implementation. When an approved immutable release is required, retain the approved snapshot and constituent revisions; record changed content as a successor. Review presentation and semantics together where the governing workflow permits it, without adding a separate approval for the publication medium.

Return the actual title, role, source revision, destination reference, approval status, checks completed, and remaining limits. Keep operation receipts and provider bookkeeping internal. Do not call unpublished files team-accessible, or call a mutable draft an immutable release.

For an explicitly selected Notion/Camunda profile, use [the Notion adapter transaction](notion-publication.md) and its real runtime contracts. Other destinations use their own supported operations; the Notion adapter does not become portable by relabeling its fields.
