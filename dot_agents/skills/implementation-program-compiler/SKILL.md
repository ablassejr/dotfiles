# Implementation program compiler

Invoke `$implementation-specification-compiler` and stop after preparing and validating the plan. Use [workspace and destinations](../epic-spec-workflow/references/workspace-and-destinations.md), [review and artifact design](../epic-spec-workflow/references/review-and-artifact-design.md), and [delivery planning](../implementation-specification-compiler/references/delivery-planning.md).

Verify the exact approved source, basis lineage, handoff, and baseline. Reuse settled intent; new program intent follows its actual approval path. The source can be repository documentation, a shared document, a wiki, or a portable package. The plan does not require a particular documentation service or tracker.

Ground responsibilities and dependency boundaries in repository evidence. Apply `$framed-engineering-sequence` and `$subtractive-design-analyzer`, grounding uncertain deletion claims before crediting them. Split work into independently useful single-PR outcomes with observable verification, approved constraints, and established ownership. Use the actual team size and existing project structure. Keep any explicitly selected three-person policy and code-mass obligations within their scope.

Verify coverage, source binding, cycles, ownership conflicts, prerequisites, shared write surfaces, and meaningful opportunities for parallel work. Native tracker relationships or one portable graph can own dependency truth; neither issue prose nor a lane diagram substitutes for checking it. Unknown owners and estimates remain explicit.

Return the coherent plan, its proposal, actual validation results, and remaining decisions. Keep source inventories and accounting in their owning records. Prepare necessary shared assets without forcing them into the issue tracker. Do not create provider records, assign work, or begin implementation from this preparation-only skill. Use provider-specific schemas only when the current plan selects their supported profile.
