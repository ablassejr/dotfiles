# Issue review and assignment

Apply the review and assignment policy established for the current program. Preserve intended owners, issue outcomes, dependencies, and the exact source revision in the plan. Do not infer an organization, team inbox, status, user identity, or fixed staffing pattern from a provider example.

When the governed program requires review before assignment, create its authorized issues without assignees, finish each issue's material decisions and exact design review, then assign the reviewed set to its approved owners. Reuse a valid prior review during execution; do not repeat settled questions. Design can use approved predecessor contracts while execution remains blocked by unresolved prerequisites.

Use `$issue-implementation` in review-only mode for those design checks. That mode never edits product code or advances execution merely because the issue exists. Keep the issue self-contained through `$issue-writing`, put implementation detail in its proposal, and preserve the actual dependency graph using the chosen tracker's capabilities or the owning portable plan.

After authorized publication or assignment, fetch the actual records and verify scope, content, owner, source binding, and supported relations. Reconcile partial writes before retrying. A static plan does not prove provider state or readiness. If the project has no requirement for a whole-program assignment gate, do not invent one solely because an adapter has it.

The [Linear/Camunda review transaction](linear-issue-review-before-assignment.md) preserves the existing automated review, assignment, and dispatch receipts for that selected profile. Other workflows use their established records and approval evidence, without simulated Camunda tasks or Linear identifiers.
