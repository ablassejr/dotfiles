# Framework routing

Use this reference to select the capability needed to understand an implementation or explain it clearly. Discover the installed skill or tool and read its applicable instructions. The table offers entry points, not a pipeline to execute in full. Use current implementation evidence whether or not any planning framework was involved. Preserve useful source identities while keeping machine data outside the reading path.

| Need in the current document | Capability to use | What the overview takes from it |
|---|---|---|
| Entry points, dependencies, behavior, or system boundaries | Claude Context and applicable code traversal; `project-exploration`, `codebase-review`, `agent-architecture-analysis`, `domain-modeling` where relevant | Verified relationships and observable contracts from the selected implementation; no exhaustive repository inventory |
| Material factual gaps or conflicting sources | Relevant code, documentation, evidence-reconciliation, or verification modules from `multimodal-research-compiler`; `documentation-lookup`, `docs-search` | Supported conclusions, uncertainty, and exact sources; reuse a Research Model when applicable without requiring one to preexist |
| Historical rationale that helps explain a mechanism | Bounded history research and `ground-me` capabilities | Sourced rationale or an explicitly labeled inference; absent history does not block describing behavior |
| A weakly supported explanation or conflicting evidence | Relevant review capabilities from `adversarial-implementation-review` or `as-built-reconciler` | Factual corrections and material limits; compare against a plan only when that comparison is requested |
| Architecture or a modeled system view | `archify`, applicable LikeC4 tools, reusable rendering capabilities from `visual-language-compiler` | A view derived from inspected implementation with readable boundaries and source fidelity |
| A diagram, user journey, spatial explanation, or screen design | `drawio-skill`, `excalidraw`, tldraw skills, Figma design or diagram skills, or a supported native renderer | The smallest readable view that explains the relevant relationship |
| Implemented behavior better understood by trying it | Actual application interactions; `playground:playground`, `visualize:visualize`, or applicable prototype/Figma tools for an explanatory model | A real demonstration or clearly labeled abstraction of implemented behavior; no invented product design |
| Browser or terminal behavior | Available browser/Chrome/computer-use capabilities; asciinema or rrweb using applicable official docs | An actual scoped capture or replay, with its provenance and limitations; see the media reference |
| A requested document, web, or presentation format | Document/PDF/presentation skills, Google Docs/Slides, frontend-slides, sites skills, or the active publisher | One reading surface with media the destination actually supports |
| An illustrative image or sound | Available image or audio generation/editing capabilities | A labeled illustration or synthetic demonstration when the medium itself adds understanding; never fabricated evidence |
| Relevant existing records or a team document destination | Available repository, Notion, Linear, document, or site tools | Optional verified context and a durable home for the implementation overview; no required planning records or delivery program |

Additional installed capabilities may be a better fit. Choose by the communication job and actual tool support. Do not install or invoke every tool in the table. If a capability is missing, use an equivalent available route when it preserves the request and the claim being made; otherwise identify the unresolved part and continue independent work.

## Reuse capabilities without requiring a planning history

A repository or deployed application is enough to begin. Establish the current scope from accessible evidence; do not require an approved basis, epic, ticket, specification release, decision ledger, or prior proposal. Reuse relevant tools and bounded research/rendering capabilities from other skills without invoking their unrelated planning, approval, implementation, or delivery stages. If a full skill's prerequisites do not fit this documentation task, choose its applicable module or another appropriate capability.

An existing design document or approved specification is optional context. Verify its claims before reuse. A plan can establish recorded intent, but it cannot prove the selected revision implements that intent or that a named environment runs it. Do not create a replacement plan, retroactive approval, or conformance matrix merely because the implementation differs. If the user separately requests compliance assessment, keep that work distinct from the current-state explanation.

This skill does not author an unimplemented proposal or fulfill the epic framework's `publish_design_proposal` job. A workflow may use the overview as evidence of existing behavior or call it after implementation, but that does not make it part of a planning approval. Existing proposals retain their own purpose. Reuse or update a current implementation overview when it already serves this scope.

Choose a suitable supported renderer for this documentation task. When work is explicitly performed inside a caller that imposes a renderer or publication contract, honor that actual contract; do not import it merely because a renderer came from the same framework. In particular, the epic framework's Figma Design/LikeC4/Archify gate applies to its governed runs, not every independent implementation overview.

When usable research already exists, check its baseline and derive prose and media from its verified claims. Research new gaps only as needed. Keep code, configuration, tests, and observed runtime evidence distinct when they describe different revisions or environments. Resolve discrepancies by inspecting the applicable source; otherwise bound the claim and state what remains unverified.

## Use tools against current documentation

For repository investigation, invoke Claude Context first and verify retrieved context in the underlying sources. Observe the user's source boundary. Check official, applicable documentation through Docs MCP Server before invoking a CLI or relying on version-sensitive capture, replay, embedding, or export behavior. Refresh missing or stale indexed documentation before building a command. If that service is unavailable, report the affected command as blocked and continue work that does not require it.

Read the selected media or destination skill before using its tools. Do not assume all editors support script embeds, all browser tools can record, or a plugin listed in a catalog is installed. A missing tool is a delivery constraint to address concretely, not a reason to send the user a catalog of technical questions.
