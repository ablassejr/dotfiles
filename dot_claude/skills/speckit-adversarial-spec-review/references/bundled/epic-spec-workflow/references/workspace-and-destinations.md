# Workspace and destination selection

This contract makes the workflow reusable across organizations, repositories, issue trackers, documentation systems, and portable files. A product name in an example, a historical skill name, or an installed connector does not select a destination or grant access.

## Resolve the current project's context

Use the current request, explicit project instructions, and verified existing associations to identify the organization, repository, audience, decision owner, and output destination. Reuse settled choices. Do not inherit a team, inbox, status, label, user identity, project ID, domain, folder, or document parent from another project. Do not create a project or move work merely to satisfy an example layout.

Distinguish the roles that need a home: the approved specification, its explanatory proposal, delivery issues and dependencies, and supporting media or evidence. One repository, page, or document may serve several roles through clearly identified sections; roles do not imply separate services or documents. Keep one authority for each fact and decision. Use the destination the user requested or the project already governs. Examples include repository documentation, an organization wiki, a shared document, an issue tracker, or a portable Markdown/HTML package. No provider is the global default.

Prepare a useful draft when the destination is unspecified. Ask only when the missing destination or audience changes the content materially, or when a concrete publication is ready and its target or authority remains unresolved. A drafting request can conclude with a portable unpublished result and its verification limits. A local path is an agent working location, not proof that the team can access the result.

## Preserve meaning across capabilities

Before writing externally, resolve the real account and target, inspect existing content, and use the destination's documented capabilities. Use native issue relationships, ownership, versions, attachments, and access controls when available. When the provider lacks a capability, keep the equivalent information in the existing governing record or one portable structured record, explain the limitation, and preserve the approved meaning. Do not invent provider IDs, statuses, relation types, revision guarantees, or adapter receipts.

Approval binds to the exact content and scope the human reviewed. A content-addressed snapshot, repository revision, or versioned document can identify that content; a mutable page title alone cannot. Keep original approval evidence and supersession history. Do not copy a complete narrative into each destination to simulate authority.

After an authorized publication, fetch and compare the actual content, associations, media, and intended audience access as far as available tools allow. Reconcile partial or uncertain writes before retrying. Report preparation, publication, readback, rendered verification, and audience access separately. A successful local validator proves only its declared checks. Preserve the viewer fallback in `design-document`; an explicitly required validation gate stays pending when unavailable.

## Select integrations deliberately

Provider-specific references and executable helpers are adapters for an explicitly selected setup. Linear, Notion, and the packaged Camunda processes remain usable when the project selects them. Their required field names, native relations, supported hosts, and process identities are not universal skill prerequisites.

The packaged `specflow` program/manifest/publication runtime implements its documented Linear/Notion/Camunda profile, including its three-person plan and destination checks. It is not a generic connector. Use those schemas and commands only for compatible inputs under that profile; do not feed another provider's URLs into them, relabel payload keys, or claim that changing skill prose adds a backend. Outside that profile, execute the skill's authoring, review, and handoff steps with the available destination tools and project records. State any missing automation accurately.

An existing orchestrator remains authoritative for its running process. Read its position and bound evidence; never simulate completion or migrate it implicitly. Without a selected orchestrator, record the actual work, decisions, approvals, and remaining steps in the current scope's records. Do not require installing an engine to draft or review a design.

Retain explicit project requirements, including team size, visual policy, approval gates, and storage rules. Treat adapter-only examples and checks as conditional. Preserve repository documentation when the repository is its chosen durable home; cleanup applies only to identified temporary work, never to canonical documents merely because they are Markdown or live beside code.
