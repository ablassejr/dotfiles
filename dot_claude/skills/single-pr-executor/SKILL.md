# Single-PR executor

## Self-contained utility setup

Use [the bundled setup instructions](references/setup.md) and [dependency manifest](dependencies.json) when this workflow needs a utility. Check availability first; the skill’s scripts install selected missing tools without relying on another skill’s setup files. Optional media, engine operations, and repository-specific toolchains are selected for the actual task. Existing session permissions and account configuration still apply.


Use the project's selected source and work records under [workspace and destinations](references/bundled/epic-spec-workflow/references/workspace-and-destinations.md). The code-mass and behavioral obligations apply to the approved scope. Commands that require a Linear/Notion manifest or fixed three-person plan apply only to that compatible profile. For other projects, perform and record the same independent normalized measurements, removal-credit checks, budgets, approved exceptions, and behavior verification against the actual source and dependency records using compatible repository tools. Do not fabricate provider fields, require three owners, or claim a packaged CLI result that was not obtained.

For human interactions and team outputs, follow [review and artifact design](references/bundled/epic-spec-workflow/references/review-and-artifact-design.md). Read it before preparing a question, review, publication, or handoff.

Require one issue or work item, one named integration owner, one approved First-Principles Basis version, completed post-basis context and reconciliation, one Code Mass Opportunity Map, a complete Code Mass Contract, an empty material decision frontier, confirmed Grounding Packets for credited removals, `ALIGNED` first-principles implementation review, `CODE_MASS_TARGETED` planning audit, adversarial design review with no blockers, and the exact approved read-back-verified implementation-design revision. A `REQUIRED` Net Addition Gate is an explicit post-implementation approval state, not permission to merge. Refuse execution when any other design gate is pending or when a native unresolved blocker points to the issue.

Use an isolated branch or worktree and keep the change inside the approved pull-request boundary. Follow [shared tool routing](references/bundled/epic-spec-workflow/references/tool-routing.md) for structural and semantic retrieval and version/environment CLI capability records, subject to stricter explicit session rules. Agent teammates may assist with bounded work, but the named owner retains integration, branch or worktree, pull request, and final verification ownership.

Implement the approved observable behavior and public contracts by removing or replacing validated machinery before adding irreducible behavior. Use the smallest nonredundant suite of behavior-driven acceptance tests that verifies the stated functionality, fix, or other change. Map the minimal acceptance criteria to observable outcomes and reuse or adapt existing coverage before adding tests. Prefer end-to-end tests through the real user or system entry point when a usable environment can exercise the path. When end-to-end execution is unavailable or impractical, use integration tests through the closest stable public boundary with the real affected components; state the concrete limitation, the boundary exercised, and what remains unverified. Do not silently substitute unit tests or count mocked provider behavior as end-to-end proof. Add separate integration checks only for material contract gaps the selected suite does not exercise, not automatically for every seam. Cover intended success and meaningful in-scope failure or recovery cases without multiplying tests for internal paths or arbitrary coverage quotas. Assert positive observable outcomes at the closest stable boundary, fake only true external or nondeterministic dependencies, and rewrite any request-relevant white-box test encountered. Do not delete useful behavior or tests, compress readable code, move complexity, add opaque abstraction, or broaden scope to create removal credit.

After each coherent slice, compare actual production, test, and combined normalized SLOC with the issue budget. Before review, commit the candidate head and write the implementation author's production, test, and combined measurements to the contract's `reported` fields. Rerun first-principles alignment against the as-built behavior, then run the verification pass of `$code-mass-auditor` to measure the same committed refs independently and reconcile the contract. Run adversarial implementation review against the committed result, and then complete any required Net Addition Gate. Finally, run the repository-selected formatting check and verify the code-mass policy against the committed base and head refs. Use `specflow code-mass-policy` only for its compatible Linear/Notion plan profile; otherwise record the equivalent independent measurements and policy assessment against the actual project records. A ratio deficit requires valid same-milestone escrow or an approved exception. A positive net delta requires the complete Net Addition Gate, including independent reviews, behavioral verification, named approvals, and the human minimum-responsible-addition confirmation.

When evidence changes the basis, semantic specification, reconciled context, or an approved implementation decision, stop and return to the earliest affected gate. When a local defect leaves the approved behavior unchanged, repair the design or implementation and rerun affected behavioral checks. Record a durable technical tradeoff as an ADR when it is costly to reverse, surprising without context, and based on a real alternative.

Prepare the PR through `$pull-request-writing`, validate the exact content before publication, and fetch and validate the saved title, description, authored comments, and document attachments before reporting publication complete.

Finish only when the pull request contains the approved boundary, the selected end-to-end acceptance suite or justified integration fallback passes, with its actual scope and remaining gaps stated, failures and recovery paths are verified in proportion to risk, the verification audit returns `CODE_MASS_VERIFIED`, the final measured report matches the issue contract, the issue retains its native pull-request association and the design proposal retains normalized evidence, the milestone ledger reflects the result, and no material gate has been bypassed.
