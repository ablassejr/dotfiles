# Tooling and adapter access

Resolve capabilities for the current task under [workspace and destinations](workspace-and-destinations.md). A listed tool is an option, not a required account, publishing destination, or authorization. Read the installed skill and current documentation for the operation before using it.

| Need | Capability to resolve | Evidence or result |
|---|---|---|
| Repository context | The project's required context tool, source inspection, structural indexes, and Git | Verified source and revision-bound lineage |
| Current tool behavior | Documentation lookup and official version-appropriate sources | Supported command, API, and capability details |
| Issue and review history | The selected tracker and repository host, or supplied records | Actual decisions, ownership, dependencies, and unresolved gaps |
| Canonical specification | The selected repository documentation, shared document, wiki, or artifact home | Exact source content, approval, revision, and readback |
| Purposeful visual explanation | Available permitted diagram, design, document, browser, and media tools under the applicable visual policy | Readable views with actual render and playback limits |
| Delivery publication | The chosen tracker or a portable task set | Self-contained issues and a verified relationship graph |
| Runtime orchestration | An already configured engine when it governs the scope | Actual process position and accepted task completion |

Do not globally install a guessed tool or require a new provider to satisfy a historical example. Missing capabilities block only the dependent action. Continue useful preparation and state unverified behavior accurately. A source that the project does not use can be marked not applicable rather than searched through another organization's account.

`$specification-publisher` publishes to the chosen documentation home. `$tasks-to-issues` prepares or publishes work for the chosen tracker. `$human-decision-loop` records assessed human answers through the scope's authorized interaction surface. `$issue-context-loader`, `$issue-implementation-designer`, and `$issue-implementation` own their respective ticket stages. Provider-named compatibility skills route to these same contracts without selecting a provider.

Spec Kit can supply specification and task drafting when the project uses it. Initialize or modify its managed files only within existing authorization, and preserve the current repository's conventions and durable documents. The packaged `specflow` runtime and [operation adapters](operation-adapters.md) implement a selected Linear/Notion/Camunda profile. Its exact schemas, three-person policy, publication jobs, and receipts apply only there. Its local content checks and other utilities may be reused independently when their public input contract fits; they do not prove provider state.

Retrieve current repository verification commands from contribution guidance, manifests, and CI. Test observable behavior and declared contracts at the relevant boundaries. Keep source inspection, local validation, CI, publication readback, deployment, and observed live behavior distinct.

The approved specification owns semantics wherever it is stored. The proposal owns its explanation. The delivery plan and work items own execution scope and relationships. A configured engine owns its process position. Temporary research and operation receipts remain internal; canonical repository documentation, approved plans, evidence required for recovery, and ADRs survive cleanup. No documentation or issue provider is excluded merely because another project used different services.
