# Per-ticket implementation loop

Use the project's selected source and work records under [workspace and destinations](bundled/epic-spec-workflow/references/workspace-and-destinations.md). The code-mass and behavioral obligations apply to the approved scope. Commands that require a Linear/Notion manifest or fixed three-person plan apply only to that compatible profile. For other projects, perform and record the same independent normalized measurements, removal-credit checks, budgets, approved exceptions, and behavior verification against the actual source and dependency records using compatible repository tools. Do not fabricate provider fields, require three owners, or claim a packaged CLI result that was not obtained.


## Design record

The linked implementation-design record contains the issue identifier, approved semantic IDs, approved ticket-level Basis ID and lineage, repository baseline, intended pull-request boundary, affected public contracts, compatibility behavior, data and migration consequences, failure and recovery behavior, security boundaries, observability, verification seams, alternatives, human decisions, Grounding Packet references, Code Mass Opportunity Map, exact introduced and removed behavior, affected files and symbols, production and test SLOC estimates, conceptual-complexity, public-API, and dependency deltas, first-principles implementation alignment, Code Mass Auditor result, adversarial implementation findings, ticket-scope framed-engineering outcomes, revision, content hash, read-back verification time, and approval state. Those outcomes identify the working frame, challenged requirements, retained, deleted, or restored work, system-level simplification, smallest useful feedback batch, justified automation, and evidence that would reopen an earlier step.

The human-readable implementation-design record is the ticket’s existing design proposal, not another narrative alongside it. Keep machine validation, accounting, and recovery fields in linked structured records. Apply [review and artifact design](bundled/epic-spec-workflow/references/review-and-artifact-design.md) for section ownership, purposeful prompts, and shared references. This design record is not copied into the issue body. Use supported native relationships or the owning plan's structured graph for dependency truth, with unsupported provider capabilities explicit.

The ticket loop resolves the existing design proposal in its selected documentation home after the ticket-level basis gate and design-dependency review. Its final planning output follows the [supervisor design document contract](bundled/epic-spec-workflow/references/supervisor-design-document.md). Reuse the resolved document or prepare a proposal in the chosen document home, publishing only when authorized after preparing its complete content. Fetch the document and issue association after publication; a partial or mismatched write remains incomplete. The supervisor-facing narrative explains the design visually with no assumed context, while detailed engineering evidence remains available through links.

## Concise loop

After basis approval, gather current evidence through `$post-basis-context-loader` and classify it through `$basis-context-reconciler`. Invoke `$framed-engineering-sequence` and `$subtractive-design-analyzer` before proposing code: test plausible ticket frames, challenge inherited requirements, identify replacement and deletion candidates, ground uncertain safety, simplify the whole affected system, choose the smallest independently useful feedback batch, and distinguish stable execution automation from early guardrails. Build the dependency graph of unresolved choices, then use `$decision-frontier-manager` and `$human-decision-loop` to ask one material question at a time with a recommendation, code-mass consequences, and `Ground me`. Grounding suspends the question. The parent records an explicit combined answer only while the packet and question bindings still match; otherwise it presents the current question or recomputes an invalidated premise.

Record each answer once in its owning decision record and update the affected proposal section and structured contract by reference. Keep the issue’s scoped behavioral contract self-contained without adding a second decision narrative. Recompute the frontier and rerun only checks affected by that answer. When no factual gap or human choice blocks the single pull request, run `$first-principles-implementation-alignment`, the planning pass of `$code-mass-auditor`, and `$adversarial-implementation-review` with separate fresh contexts. Repair and rerun affected design gates until alignment, `CODE_MASS_TARGETED`, and no blockers are recorded. An estimated positive delta remains `net-addition:review-required`. Publish the final supervisor proposal, fetch and inspect its rendered content, compare its revision and content hash, and record human approval against that exact read-back-verified document and design source.

## Implementation and verification

In program review-only mode, return the completed issue review after exact supervisor approval. Apply the current program's review-before-assignment policy; a configured engine enforces its real completion gate. Assigned execution verifies and reuses that review. For standalone execution, continue after its design gates pass. Only then invoke `$single-pr-executor`. It uses an isolated branch or worktree, keeps the change inside the approved PR boundary, continuously compares actual SLOC with the budget, uses a minimal behavior-driven acceptance suite, preferring end-to-end tests through the real entry point and otherwise integration tests across real affected components. Reuse existing tests; add only scenarios needed to verify the stated outcome and meaningful in-scope failure or recovery behavior. Record any end-to-end limitation and the actual boundary exercised; add separate seam checks only for material gaps in that suite. Assert observable behavior at the closest stable public boundary. Fake only true external or nondeterministic dependencies. Rework any request-relevant white-box test encountered. Against the committed candidate, record the implementation author's reported measurements, rerun alignment, run the independent Code Mass Auditor verification pass, run adversarial review, complete any Net Addition Gate, and run the final `code-mass-policy` check before merge.

When implementation exposes a semantic change, stop and return to the owning specification and its approval workflow. When evidence changes the ticket frame, requirement, retention decision, design, feedback path, or automation premise, return to the earliest affected framed-engineering step and invalidate only dependent approvals. When it exposes a local implementation choice, update the design record and decision frontier. When verification fails, repair the contract or implementation and rerun affected checks. Use [pull-request-writing](bundled/pull-request-writing/SKILL.md) for the PR description and its publication readback. Retain the native PR association on the issue and put detailed verification records in the design proposal.

[Approval economy](bundled/epic-spec-workflow/references/approval-economy.md) verifies unchanged basis inheritance and routes final presentation feedback directly to proposal publication. New intent requires a distinct approved basis; semantic feedback returns to implementation design.

See [the program review and assignment contract](bundled/epic-spec-workflow/references/issue-review-before-assignment.md) for issue coverage, review receipts, and automatic reuse.
