# Shared project resources

Give the team access to the proposal and the evidence or media it needs through the project's chosen documentation or artifact home. Reuse accessible authoritative references. A tracker project Resources area is one possible adapter, not a required second destination or a reason to upload duplicate narratives.

Prepare only artifacts with a distinct reader and purpose. Each explains its role, audience, status, and governing source; a caption can provide that context for media. Keep scratch work, alternate drafts, raw extracts, operation receipts, and comparison logs internal. A snapshot needed for exact-revision recovery is labeled archival evidence and stays outside the main reading path.

Before requesting review, make review-critical content available in the selected review surface or clearly state the unpublished draft boundary. Do not promise inaccessible supporting evidence as if it were already shared. For team delivery, verify descriptive references, required media, and intended audience access as far as tools allow. A local path or successful upload response alone does not establish access.

Use the current task's publication authorization and destination. Reconcile partial uploads before retrying; compare fetched content or downloaded bytes when appropriate. Preserve existing resources and source relationships. Ask only for a genuinely missing target or access decision after preparing the concrete result. A drafting request does not require creating a tracker project, workspace, or shared account.

An explicitly configured Linear/Camunda program can require the [Linear project-resource transaction](linear-project-resources.md), including its inventory, byte readback, audience verification, and job receipt. That specialized gate remains binding for that process. It does not impose Linear storage on another project's documents or issues.
